# Do's and don'ts

## Do

- Search project memory and current code before creating a new implementation pattern.
- Link rules and solutions to code, tests, schemas, or reproducible commands.
- State applicability, verification level, and exceptions explicitly.
- Keep durable knowledge small enough to review in a pull request.
- Supersede or archive obsolete guidance as part of the change that replaces it.
- Sanitize errors, payloads, and screenshots before documenting them.

## Don't

- Do not treat chat history or generated summaries as authoritative memory.
- Do not record speculative conclusions as verified facts.
- Do not duplicate the same rule across several active documents.
- Do not copy credentials, private keys, personal data, or production records into the repository.
- Do not apply an old solution without checking versions, code paths, and current tests.
- Do not mark work Complete when documentation or required verification remains outstanding.
